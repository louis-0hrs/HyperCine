## Result and scope

The original SDK can read a spatial wavelet's lowpass coefficients before their
producer has written them. The faulty readiness predicate is
`BANDS_ALL_VALID` in `upstream/Codec/image.h:230`: equality of the *started* and
*valid* masks accepts `0xE == 0xE`, even though bit 0 is absent in both masks.
This is a producer/consumer dependency error, with uninitialized or partially
written coefficient memory as its data source. Clearing the caller's output or
reseeding its random generator cannot establish that dependency.

The new Windows experiment links this mechanism to **FULL BGRA**, as well as
HALF, on a retained 1920x1080 Phase2A synthetic capture. It includes a natural
failure under observation, deliberate ordering violations, and a channel-specific
ordering control. The generated diagnostic translation unit is separate from
the immutable SDK and is never linked into production targets.

The historical [#205](https://github.com/louis-0hrs/HyperCine/issues/205) was
closed after identical-input SDK attribution; it did not resolve the underlying
SDK defect. [#160](https://github.com/louis-0hrs/HyperCine/issues/160) already
had bounded HALF readiness-race evidence. This investigation demonstrates the
same faulty dependency in the FULL path of a Phase2A capture. It does **not**
claim that every historical #205 failure had this exact instruction ordering.
The retained guard-smoke packet's identity with the original #206 capture has
not been established; equal byte length alone would not establish it.

Measured transform type is SPATIAL (`0`); all three channels execute index2 and
index1. FULL and HALF share this producer/consumer chain. Their downstream
output construction differs. This packet does not exercise the FIELDPLUS/GOP2
temporal inverse, so the independent ASan overread in `temporal.c:9606` cannot
explain this particular trace.

An additional source exposure is the unlocked readiness recheck after claim,
which can discard already-claimed work. That mechanism was separately studied
in [#195](https://github.com/louis-0hrs/HyperCine/issues/195). The experiment here
does not inject lost work and does not attribute its cases to that exposure.

## Native experiment

Environment: Windows build 26200, AMD64 Family 25 Model 116, 16 logical CPUs,
MSVC 19.44 Release. The executables link the CPU SDK only; CUDA is absent.
`TAG_CPU_MAX=8` results in **four** entropy workers in the observed probe;
`TAG_CPU_MAX=1` results in zero entropy workers. These are SDK metadata controls,
not affinity emulation. Each process decodes exactly once with active metadata,
fixed caller seed `0x1337BEEF`, aligned output and a 4096-byte output guard.
Output prefills alternate `0x00` and `0xA5` in every arm. Timeouts are bounded;
no retry-to-green occurs.

Input host SHA-256:
`fc046231223e537bb221524b2d6f9c0d9f24a71ea23f79deb140f44f7bd063c8`.
The retained host/device samples are both 900396 bytes and differ only at byte
71 (frame number 11 versus 14). The complete identity, source and binary hashes
are in [provenance](evidence/sdk-rca-2026-10-28/provenance.json) and
[the plan saved before execution](evidence/sdk-rca-2026-10-28/plan.json).

Three probe modes retain the SDK's arithmetic, flags and packet bytes:

* **Observe:** record flags under the existing writer lock immediately before
  the actual inverse; hash the resulting lowpass plane before publication.
* **Induce ch1:** hold channel1/index2 before its write until channel1/index1
  finishes consuming that buffer. The only intervention is a bounded event wait.
* **Order ch1:** wait in channel1/index1 for channel1/index2 to finish writing.
  This diagnostic orders one dependency, not the other channels or all SDK paths.

The observer matches the consumer's input allocation to the producer's output
allocation internally, without exposing addresses. Final matching uses the
**first** completion of the allocation; HALF may execute a producer more than
once. Event numbers denote hook reservation order, not individual load timing.
The induced cases have the stronger witness `consumer begin < consumer end <
producer begin`, with the wait signalled and the input masks both `0xE`.

| Arm (8 fresh processes each) | FULL outputs differing from stable control | HALF outputs differing from stable control |
|---|---:|---:|
| Stock SDK, CPU_MAX=1 | 0/8 | 0/8 |
| Stock SDK, CPU_MAX=8 | 0/8 | 1/8 |
| Observer, CPU_MAX=1 | 0/8 | 0/8 |
| Observer, CPU_MAX=8 | 1/8 | 0/8 |
| Induce channel1 read before write | 8/8 | 8/8 |
| Order channel1 write before read | 2/8 | 0/8 |

All **96/96 calls returned SDK success and retained their output guard**. Those
returns do not certify pixel correctness. The final FULL observation failure
changed **6,195,775 bytes**, maximum byte delta **238**. Its channel0 and channel2
index1 outputs were already wrong before color conversion. The corresponding
index2 producer hashes matched the control. This localizes the problem to the
dependent reconstruction rather than to differing encoded entropy.

The induced channel1 lowpass was wrong **8/8 FULL and 8/8 HALF**. Ordering that
dependency restored the channel1 lowpass **8/8 in both resolutions**, while two
FULL cases still had a wrong **channel2** lowpass. Thus the experiment positively
demonstrates why a channel-specific workaround cannot repair the entire SDK.
Producer-before-consumer ordering must cover every channel and required band.
It also shows why an early entry alone is insufficient to predict wrong pixels:
the publisher can catch up before a particular coefficient load.

The earlier exploratory `matrix-v1` had a diagnostic bug: it attempted to lock
an uninitialized entropy lock with zero workers. `matrix-v2` selected the last
rather than first matching producer in traces with duplicate HALF transforms.
Both were corrected before the final 96-call ledger. They are not included in
the table. One earlier v2 FULL failure changed 354715 bytes; that interim
observation must not be substituted for the final ledger's counts.

## Dithering and initialization conclusions

YUY2's inverse output path does contain `rand() & mask` rounding, for example
`InvertHorizontalStrip16s.c:3872â€“3888`. Its random-state ownership is CRT-specific:
MSVC `srand` seeds the **current thread**, as documented by
[Microsoft](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/srand?view=msvc-170).
The old test comment asserting shared CRT state on Windows was incorrect and is
corrected. A caller seed does not reset an existing worker's sequence.

The wrong plane in this experiment is measured before final output dithering.
The traced spatial lowpass/Descale coefficient reconstruction uses deterministic
integer arithmetic. Hence output dithering cannot account for the observed
wrong internal lowpass or the controlled read-before-write witness. This does
not imply that all SDK output formats are free of separate dither variation.

The single-CPU controls agree across both output prefills; errors also occur in
internal planes. Caller-output initialization is therefore not the explanation
for these failures. The allocation path permits old heap contents in the missing
input band; in a racing call, a mixture of old and newly written coefficients is
also possible. No heap poison was injected, and no exact provenance is claimed
for every stale coefficient. Zero-filling that allocation would make some wrong
results more reproducible while leaving the dependency bug intact.

## #120 test interpretation and release boundary

`test_phase2a` now parses and verifies packet equivalence, allowing only the
parsed frame-number tag value to differ. Coefficients, entropy, payload, geometry
and API errors remain fatal. Pixel equality and the original 35 dB threshold are
recorded independently. The existing test-only decision contract from the
reviewed #208â€“#210 development stack was reused for Phase2B/C/D and covered by
its SDK-free negative tests; no production encoder or CUDA decoder changed.

| Result | Exit | Interpretation |
|---|---:|---|
| Strict coefficient/bitstream/API/resource failure | 1 | Real test failure, never converted to an oracle skip |
| Original SDK unstable or unqualified pixel reference | 77 | Explicit CTest skip, no pixel-accuracy PASS |
| Qualified independent oracle and all checks pass | 0 | Contract supports this; no current Phase2 caller asserts qualification |

Repetition diagnoses variation; stable repeated outputs do not qualify this
SDK as an independent oracle. The separate `test_reference_release_gate`
deliberately fails with `BLOCKED_ORACLE_NOT_QUALIFIED`. This prevents an otherwise
green CTest aggregate with four skips from becoming release certification.
`ctest -L release` selects the explicit release condition. A future qualified
oracle must replace that condition with evidence, not an environment bypass.

## Reproduction

### Validation on this checkout

The complete requested command, `ctest --test-dir build -C Release
--output-on-failure`, ran all 47 registered tests in **1883.24 seconds**:
44 passed, two skipped and the explicit release gate failed. Inspection of its
output exposed stale Phase2C/D objects: copying the reviewed source files had
retained October 20 timestamps, older than their October 27 objects. Their two
PASS results therefore **do not validate the new oracle gate**.

Both sources were forced through compilation (verified compiler output), then
all six affected tests were rerun on the final executables in **33.22 seconds**:

* `test_reference_oracle`: PASS, including fatal encoder/API failures,
  missing evidence, packet-header/payload distinctions and unqualified quality.
* `test_phase2a`, `test_phase2b`, `test_phase2c`, `test_phase2d`: all strict checks
  completed; each returned 77 / `BLOCKED_ORACLE_NOT_QUALIFIED`. Phase2A reported
  `FRAME_NUMBER_HEADER_ONLY`; its instability classification uses only the two
  repeats of the identical host packet. Different frame headers are recorded
  separately. Phase2C/D observed 12/21 decodes and retained their byte checks.
* `test_reference_release_gate`: expected FAIL with the explicit qualification
  blocker. This is not a CUDA correctness failure or a successful release gate.

The other 41 tests passed in the full invocation, including the 1261.17-second
Phase2FA stress test. The full long-running suite was not repeated after the two
object rebuilds; the final verification is **full suite plus focused rebuild
verification**, not a claimed single final 47-test green run. See
[validation.json](evidence/sdk-rca-2026-10-28/validation.json) for both inventories
and final executable hashes. The RCA ledger verifier also passed its four
deliberate negative controls, and all recorded RCA source/binary hashes were
rechecked. `git diff --check` on the changed files and
`git status --porcelain upstream/` were clean. No commit, merge, performance
claim or release was made.

```powershell
cmake -S . -B build-rca -DHYPERCINE_ENABLE_CUDA=OFF -DHYPERCINE_BUILD_BENCHMARKS=OFF -DHYPERCINE_BUILD_SDK_RCA=ON
cmake --build build-rca --config Release --target sdk_rca_stock sdk_rca_probe

python tests/sdk_rca/verify.py docs/evidence/sdk-rca-2026-10-28
```

The checker rejects a truncated ledger, an SDK error, a missing wait witness and
a falsely ready induced input. Future runs can be inconclusive or fail its
causal criteria; do not discard such runs. Hooks have finite event capacity and
bounded waits. They are an opt-in Windows diagnostic, not a synchronization
implementation suitable for deployment. A safe SDK redesign still requires
per-band dependencies, synchronized publication, exactly-once execution,
worker forward progress, all output channels, generation/lifetime tracking,
and fail-closed error propagation. Frozen `upstream/` remains untouched.
